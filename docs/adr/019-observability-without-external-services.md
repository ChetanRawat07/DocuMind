# ADR-019: Observability without external services

- **Status:** Accepted
- **Date:** 2026-11-03

## Context

Phase 11 makes system behavior traceable: a request, the job it queues, the worker's run, the AI
calls and the outcome must be connectable. The demo runs on free hosting (ADR-009) with no
budget for a metrics stack or an error service. Logs and error reports must never carry document
content or secrets.

## Decision

- **Correlation ids are generated by the API**, one UUID per request, returned in `X-Request-Id`
  and in error bodies. Incoming ids are ignored.
- **Propagation with `AsyncLocalStorage`.** The id is stored on audit entries and on the
  processing job (`processing_jobs.request_id`). The worker restores it, with the job id, while
  it runs the job.
- **Structured logs** use Nest's own `ConsoleLogger` in JSON mode, with structured fields
  flattened to top-level keys, key-based redaction, and a subclass that adds the correlation ids.
  No logging library is added.
- **Errors are tracked in the logs** (5xx with stack, failed jobs with codes). No Sentry: it
  would send stack traces and paths to a third party, and needs a secret.
- **Metrics come from the database.** Step durations are stored on the job, and the Processing
  screen's numbers are SQL aggregates over `processing_jobs`. No Prometheus endpoint.
- **Users see their own audit trail:** their actions, and the system's actions on their documents.

## Alternatives

- **Accept a validated incoming request id.** It would join a proxy's or the browser's trace, but
  a client could reuse or choose ids and muddle the logs.
- **pino or OpenTelemetry.** Richer features and the standard for tracing, but new dependencies,
  and tracing needs a collector the demo cannot host. The ids and fields used here map directly
  onto OpenTelemetry attributes if it is added later.
- **Sentry (free tier).** Grouped errors and alerts, but a third party receives error data.
- **Prometheus with prom-client.** The usual metrics answer, but it needs a scraper and dashboard
  and must be kept off the public internet. It is also per-process and resets on restart, while
  the database already holds the durable job history.

## Trade-offs

- **No alerts or dashboards** beyond the app's own screens and the host's log search.
- **Database-computed metrics cost queries:** each Processing screen load runs two aggregates over
  the user's jobs.
- **Only the latest timings:** one timing per step and job, from the last attempt that ran it.
- **Context can be lost in callbacks:** a callback that runs outside the request's async context
  logs without the id. The file-stream error handler reads it from the response header instead.

## Consequences

- How to trace a request and what each log line holds:
  [docs/operations/observability.md](../operations/observability.md).
- Phase 12 analytics can reuse the job durations, and the audit log for review rates.
- Phase 16 should point the hosting platform's log search and alerts at the JSON fields.
